## Status

The current VPM implementation has a review-gated, source-only GitHub publication flow. Publishing is not an immediate release: it submits a change for review. Registry service availability and account permissions must be checked separately.

## Package model

Packages are represented by repository directories and concrete versions. The package name and version come from `vpm.toml`, not a name argument to publish.

## Validate before submitting

```bash
vpm publish --dry-run
vpm publish owner/repository --dry-run
```

Dry-run validates and builds a publication plan locally without network submission. The default registry configured in the source is `duongonix/vpm`; an explicit `owner/repository` selects another registry.

Without `--dry-run`, VPM uses `VPM_TOKEN` or `GITHUB_TOKEN` to create a branch, commit package source under the package/version directory, and open a pull request. This is an external write: run it only when ready to submit, with appropriate permissions.

## Package requirements

Provide `src/mod.vut` or at least one `[[bin]]` entry. Registry packages publish native source via `[native] build`, not prebuilt native libraries. `native-artifacts.toml` is generated by trusted CI and must not be submitted by publishers.

Review the full package directory for secrets before publishing. The source collector excludes build/cache/VCS directories and certain metadata, but it is not a secret scanner or a promise to apply every custom ignore rule.

## What to prepare

Keep package metadata accurate, use a valid semantic version, document the public API, and test supported platforms. Do not put credentials in `vpm.toml` or `vpm.lock`.
